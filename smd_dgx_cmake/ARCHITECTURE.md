# smd_dgx architecture

Цель: рабочий эмулятор (Genesis Plus GX) с debug-API, к которому подключаются
клиенты. Основной — IDA-плагин (порт связки ida + gens из smd_ida_tools2),
плюс standalone Qt-приложение и MCP-сервер для агентов.

```
┌────────────────────────────────────────────────────────────────┐
│ Hosts                                                          │
│   smd_dgx_qt6  — standalone Qt app                             │
│   smd_dgx_ida  — IDA 9.3: статически линкует gx_core +         │
│                  debugger, эмулятор на своём потоке ТОГО ЖЕ    │
│                  процесса. ДВА debugger_t в одном бинаре:      │
│                  68000 (запускает) и Z80 (подключается).       │
│   MCP-сервер   — Python поверх моста, для агентов              │
├────────────────────────────────────────────────────────────────┤
│ Views (frontends/qt6/views/*)                                  │
│   Чистые QWidget'ы. Зависят ТОЛЬКО от debugger/DebugState.h    │
│   и debugger/IDebugBackend.h — ни одного инклюда ядра.         │
│   IDA — Qt-приложение, поэтому те же виджеты встраиваются      │
│   в плагин. Состояние вьюшек — ViewSettings (общий ini).       │
├────────────────────────────────────────────────────────────────┤
│ Debug API                                                      │
│   IDebugBackend  — синхронный интерфейс состояния. Две         │
│                    реализации: GpgxBackend (in-proc) и         │
│                    RemoteBackend (поверх сокета).              │
│   DebugApi.h     — DebugCommand/DebugEvent для транспорта.     │
├────────────────────────────────────────────────────────────────┤
│ Transports (debugger/)                                         │
│   InProcTransport — очереди между потоками одного процесса.    │
│   BridgeServer    — строчный протокол на loopback: MCP,        │
│                     Z80-база, любой внешний клиент. Порт       │
│                     выбирается сам (27042+), ping говорит,     │
│                     чья это игра.                              │
├────────────────────────────────────────────────────────────────┤
│ Emulator core                                                  │
│   gx_core (core/*) + core/debug/cpuhook (HOOK_CPU)             │
│   GpgxBackend вешает cpu_hook, ведёт паузу/степы. Хуки:        │
│   исполнение и доступ к памяти на ОБОИХ процессорах.           │
└────────────────────────────────────────────────────────────────┘
```

Тесты: `tests/` — 42 кейса поверх `smd_dgx_emu` (без Qt, без IDA, без SDL),
на синтетическом ROM, который они собирают сами. `ctest` или
`smd_dgx_tests[ подстрока]`.

## Контракты, которые нельзя ломать

- **Байт-порядок**: ядро на LSB_FIRST хранит ROM/RAM68K/VRAM word-swapped.
  `readMemory`/`readRegion` отдают ЛОГИЧЕСКИЙ порядок (backend делает `^1`).
  Сырые указатели `VdpState.vram/sat` — как в ядре: логический байт A =
  `ptr[A^1]`; cram/vsram читаются 16-битными LE-словами.
- **Регионы памяти** (id стабильны): 0 ROM, 1 RAM 68K (0xFF0000), 2 RAM Z80
  (0xA00000), 3 VRAM, 4 CRAM, 5 VSRAM, 6 Regs M68K, 7 Regs Z80, 8 Regs VDP.
  Паритет с hex-редактором Gens.
- **VDP-брейкпоинт-пространство** (наследие протокола IDA): VRAM +0x0000,
  CRAM +0x10000, VSRAM +0x20000; в IDA это псевдосегменты от 0xD00000.
- **Codemap** (`changed`: executed pc -> predecessor) шлётся с каждым
  pause/stop событием и атомарно очищается — IDA строит по нему код.

## IDA-плагин

IDA 9.3 — первая IDA на стоковом Qt 6.8.2, том же, что и наши вьюшки.
Работает: debugger_t + HT_IDD, регистры, память через регионы, брейкпоинты
(исполнение и данные, оба процессора), пошаговое выполнение, стек вызовов,
codemap → `auto_make_code`, вьюшки в доках, пресеты раскладок, сейв-стейты,
ROM-патчи, декодер констант в листинге.

Грабли, которые стоили дорого и остаются в силе:

- **IDA и Qt НИКОГДА в одном TU.** `pro.h` и `qbytearrayalgorithms.h` оба
  безусловно определяют inline `qstrlen`/`qsnprintf`/… (на Qt5/IDA≤9.1 такого
  не было). Граница: `ida_dock.cpp` = IDA-glue без Qt, `ida_views.cpp` = Qt без
  заголовков IDA, между ними `void*` (TWidget→QWidget) в `ida_views_shared.h`.
  По той же причине `EmuHost::emit` называется `emitEvent`.
- **Только RELEASE.** Debug тянет `Qt6Widgetsd.dll`, а IDA несёт release-Qt и
  release-CRT. Смешивать нельзя — плагин обязан подхватывать уже загруженный
  IDA Qt.
- **Qt IDA собран в namespace** (`QT_NAMESPACE=QT`). Заголовки и moc берутся из
  обычного Qt, а линкуются import-либы из `<sdk>/lib/*_qt`. Любое голое
  предобъявление Qt-класса надо оборачивать в `QT_BEGIN_NAMESPACE`.
- **`dbg` — один слот на процесс**, и каждый debugger-плагин в него пишет.
  Оба plugmod'а проверяют `dbg == &свой_debugger_t` перед обработкой события:
  таблицы регистров разной длины (54 против 26), а буфер IDA размеряет по
  `::dbg`. Это нужно даже с одной базой.
- Единый `ida.dll` (не ida/ida64) — 9.x перешла на ea64 везде.

Сборка (RELEASE, см. выше):
```
cmake --preset x64-release -DIDA_SDK_DIR=<sdk> -DIDA_INSTALL_DIR=<ida>
cmake --build ../builds/x64-release
```
Пост-билд копирует модули в `<IDA>/plugins` и `<IDA>/loaders`; если IDA
запущена и держит файл, это печатает строчку и НЕ валит сборку.

## Отладка Z80 рядом с 68000 (две базы, один эмулятор)

Одна IDB = один процессорный модуль (`inf.procname` — одно поле, не на
сегмент), поэтому игру и звуковой драйвер в одной базе не разложить. Схема:
**68000-база запускает эмулятор, Z80-база к нему подключается**.

```
 IDA #1 (PLFM_68K)                       IDA #2 (PLFM_Z80)
 smd_dgx_plugmod_t                       smd_dgx_z80_plugmod_t
   dbg = &debugger                         dbg = &z80_debugger
   EmuHost (эмулятор в процессе)           RemoteBackend  ──┐
   BridgeServer :27042  ◄──────────────────────────────────┘
```

- `debugger/RemoteBackend` — `IDebugBackend` поверх сокета моста. Все вьюшки
  зависят только от интерфейса, поэтому в Z80-базе они заработают тем же кодом.
- Один бинарь, два `debugger_t`: `init()` смотрит на `PH.id` и отдаёт нужный
  plugmod. `ev_start_process` в Z80-базе не запускает эмулятор, а коннектится.
- События мост не пушит (линейный протокол), их **опрашивают**: поток
  `poll_loop` дергает `events` раз в 20 мс. Любая пауза (даже по 68000-брейку)
  превращается в `PROCESS_SUSPENDED` по адресу Z80-PC — база умеет показывать
  только Z80-код.
- Брейкпоинты Z80-базы всегда уходят с `cpu=z80`, поэтому одинаковые числовые
  адреса в двух базах не пересекаются. Условия у них **не поддерживаются**:
  вычислять их должна была бы IDA, а протокол строго client-initiated.
- Отсоединение = detach: свои брейки снимаем, `resume`, сокет закрываем —
  эмулятор принадлежит другой базе и продолжает жить.
- `Z80Regs.bank` — база окна $8000..$FFFF в адресном пространстве 68000
  (`zbank`). Без него окно пустое, а драйверы гоняют через него сэмплы.
- Загрузчик драйвера: `ida_loader/z80_loader.cpp` (порт из smd_ida_tools2) —
  сегменты, имена портов YM2612/PSG/банка, энумы регистров YM2612.
  Дамп берём **живой** (Debugger → SMD patches → Dump Z80 driver...): в ROM
  драйвер часто лежит сжатым, а в RAM он уже развёрнут.

## Мост и агентская петля

`BridgeServer` — строчный протокол на loopback, намеренно тупой: одна команда
в строку, один ответ в строку, `ok ...` или `err ...`. Никакого JSON в C++,
вся структура живёт в клиенте. Поток на клиента; команды между собой НЕ
сериализуются (общий лок дал бы одному клиенту вешать всех на кадр).

Примитивы, на которых держится работа агента:

| Команда | Зачем именно она |
|---|---|
| `wait [ms]` | Блокируется до остановки и называет причину: pc, cpu, **id брейкпоинта**. Опрос заменяет её только ценой сожжённого ядра |
| `frameadv n` | Ровно n кадров. Заменить нечем: под отладкой машина не привязана к реальному времени, ввод нельзя оттаймить сном |
| `search`, `snap`/`diff` | Поиск и сравнение регионов на стороне эмулятора — иначе 64 КБ ASCII-хексом каждый раунд |

События опрашиваются, а не пушатся: строчный протокол не умеет вклинивать
неожидаемый вывод между запросом и ответом. Очередь на каждого клиента,
переполнение честно сообщается как `dropped`.

**Мультисессии.** Порт выбирается из диапазона 27042+16 (или `$SMD_DGX_PORT`),
`ping` отвечает pid, портом, вычисленной контрольной суммой ROM, серийником и
названием. Клиенты **сканируют**, а не читают файл опубликованных портов: файл
от упавшей сессии врёт, отвечающий сокет — нет.

Две игры = два процесса, и иначе быть не может: ядро gpgx — глобальное
C-состояние, а `g_gpgxBackend` (хук CPU) один на процесс. Второй `GpgxBackend`
в том же процессе молча отбирает хук у первого.

Тихий реконнект в MCP переподключается к **тому же** порту намеренно:
переоткрытие поиска могло бы посадить сессию на другую игру, и все дальнейшие
ответы были бы про то, чего никто не спрашивал.

## Что состояние переживает перезапуск

`frontends/qt6/ViewSettings` — один ini под `GenericConfigLocation`, общий для
обоих хостов (не `AppDataLocation`: он выводится из имени приложения, и плагин
писал бы в каталог IDA). Сохраняются геометрия окна и раскладка доков,
настройки экрана, зум VDP Ram, план/зум Plane Explorer, каталог последнего ROM.
Список RAM Watch — через тот же формат `.wch`, что и кнопки Open/Save, так что
автосейв читается руками и в Gens.

## Статус вехи (2026-07-30)

Ветка `feature/smd-dgx`, всё запушено.

Работает и покрыто тестами: байт-порядок, регионы, упаковка CRAM, шаг и
step-over на обоих процессорах, брейкпоинты (исполнение и данные, с учётом
ширины доступа), сейв-стейты, весь протокол моста, мультисессии.

**Не проверено руками ни разу:**
- Z80-связка целиком через интерфейс IDA (дамп → загрузчик → attach).
- Сборка на Linux и macOS. Причины, по которым там заведомо не собиралось,
  устранены (SDL-звук, SocketCompat, опциональный SDL-фронт, платформенные
  суффиксы модулей), но сама сборка там не запускалась.
- Многое из накопленного раньше: VDP-брейкпоинты, условия, ROM-патчи,
  декодер `J`, A/F-line, менеджер сохранений, пресеты.

**Известно сломанным** (полный список — в отчётах аудита): `EmuHost::invoke`
по таймауту оставляет указатель на умерший стек; `stepOver` не проверяет
паузу; нет `DBG_HAS_UPDATE_CALL_STACK`; `J` затирает существующий комментарий;
`RemoteBackend` рапортует успех через `|| true`; CRAM/VSRAM-брейки не
маскируются `&0x7E`.
